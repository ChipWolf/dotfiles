# Global agent rules

These rules apply to every coding session, across every project.

**Precedence:** the **closest `AGENTS.md`** to the files you're changing wins. This file holds cross-tool defaults; project and directory `AGENTS.md` files override on conflict. See the [Memory](#memory) section for where each file lives.

---

## Always active

These constraints are unconditional. Apply them without being asked.

- **No em dashes.** Use commas, colons, or restructure the sentence. Never generate inline `—` or `&mdash;` as punctuation. (Markdown horizontal rules: `---` alone on a line is fine.)
- **Never hand-type a git object id; derive it.** Expanding an abbreviated SHA from memory fabricates the tail and fails confusingly downstream (a `--force-with-lease=<ref>:<sha>` with an invented full SHA rejects with "stale info" even when your intent was right). Always compute full ids with `git rev-parse <short-sha>` (or capture them from command output) before using them in lease values, pushes, or API calls.
- **Never guess schemas or APIs.** Read the authoritative source first: Go structs, official docs, or the project's own examples. Blog posts and AI-generated examples are not acceptable. Read it **at the version you pin**: a default-branch clone's docs describe options that may not exist in the tagged release you deploy (a flag added after `vX.Y.Z` makes the pinned binary refuse to start with "unknown flag"). Clone the tag (`git clone --branch <tag>`) and grep the option definitions there before committing a config that uses them.
- **Run a validator or linter at the version the gate runs, and confirm you actually got that version.** A validator's error set is version-specific, so an older binary reports confident false positives on options that are valid in the pinned major, and "fixing" those means breaking working config (renovate-config-validator 37 rejects `platformCommit: "enabled"` and `packageRules[].overrideDepName`; both are valid in 44, which is what CI ran). Derive the version from the thing that invokes the tool rather than from latest: a GitHub Action's `action.yml` carries the default its workflow inherits when the workflow does not set the input. Then print the resolved version before trusting a single result, because `npm install <tool>` silently falls back to an ancient release when the local runtime sits outside the package's `engines` range instead of failing (node 26 against `engines.node: ^24.11.0` installed renovate 37 in place of 44). Install the exact version (`npm i <tool>@X.Y.Z --force`) once you know it.
- **Prove a declarative matcher fires by running the tool's own matcher over the real tree, not by reading the pattern.** Config that selects files or extracts values by regex or glob (Renovate managers, CI `paths:` filters, lint include/exclude globs, CODEOWNERS, cache paths) fails silently when it matches nothing: no error, the behaviour just stops. Most such tools expose the matching logic as an importable function (Renovate's `modules/manager/custom/regex` `extractPackageFile`, `@actions/glob`), so run it against the checked-out tree and count what comes back before editing or deleting the rule. That turns "this looks stale" into a measurement, and it separates the three ways a rule dies: matching no file at all, matching a file that no longer carries the marker, or extracting a value the declared versioning then rejects. Quote the counts in the commit, since the next reader cannot re-derive them from the diff. Suspect this class whenever a repository's paths have been rewritten wholesale, for example a monorepo assembled with `git filter-repo --to-subdirectory-filter`: the prefix silently orphans every config a tool discovers at a fixed path (GitHub reads `.github/` only at the repo root, Renovate only reads root config filenames) and every path pattern inside the configs that were carried across. A forgotten one looks identical to a handled one, so enumerate them deliberately instead of waiting to trip over one: list the tools that discover by fixed path, and grep the migrated configs for patterns that were not re-prefixed.
- **A browser-automation key press is not a user key press.** Synthetic `Return`/`Enter` from an automation pane can arrive as a keydown without the character event that triggers implicit form submission, so a form that works for humans looks broken in the pane. Before touching the page, prove the handler with `form.requestSubmit()` or a dispatched `KeyboardEvent` from the page's JS console; if that works, the page is fine and the automation is the instrument at fault. Adding an explicit `keydown` Enter handler is harmless, but it is not a fix for a bug that was never there.
- **Verify a dependency supports the target platform before designing around it.** Before locking in a spec that depends on a third-party tool on a specific OS, confirm artifacts and source actually support that OS: run `gh release view --json assets` to see what's published, check the upstream CI matrix for the OSes it builds, and grep the source for OS-specific imports or build tags. Project names and descriptions don't imply cross-platform binaries; many "general" tools are Linux-only at the artifact level even when the README sounds portable.
- **Diagnose from logs, not theory.** When investigating a failure (CI, runtime, hang, regression), the last lines of output before the failure are ground truth, not a guess based on which script's name matches your current hypothesis or which prior bug looked similar. If the visible log doesn't pin the cause, add a diagnostic and re-run rather than speculate further. When reporting findings, mark claims as observed ("log line N says X") versus suspected ("I think Y because…") and never let suspicion harden into assertion without evidence.
- **Verify a subagent's claims about mutable repo state before relaying or acting on them.** When a subagent reports that a PR was merged or closed, a branch or tag exists, or CI passed, treat it as a hypothesis: confirm against the authoritative source (`gh pr view --json state`, `git log origin/<default-branch>`) before it shapes your report or your plan. A commit hash being findable locally (`git log --all`) proves nothing about the remote default branch; local object stores accumulate refs from other worktrees and stale fetches, which makes such claims look corroborated when they are not. Observed failure: a review subagent asserted an open PR had "since been squash-merged as <sha>", the controller relayed it to the user, and a direct `gh pr list` one step later showed the PR still open. The same discipline applies to a subagent's causal hypotheses: an exploration agent's "mechanism candidate" for a bug is a lead, not a diagnosis, so before implementing a fix based on one, check the mechanism against the runtime's actual semantics and against the symptom's recovery profile (a cause that self-heals on the next event cannot explain a symptom that persists until restart or remount). Observed near-miss: an agent plausibly blamed a shared THREE.js texture cache being disposed for a persistently blank canvas, but disposed textures re-upload from their retained image on the next render, so that mechanism could not produce the persistent symptom; the real cause was an unretried failed fetch.
- **Contradictory observations mean a bad instrument, not a new theory.** When two measurements of the same thing disagree (a value healthy at line N but "null" at line N+1, a passing run and a failing run of identical code), stop hypothesising and instrument the exact divergent reads side by side in one run; the discrepancy is the bug's address. Treat tool-reported metadata as suspect until verified: logcat's tid column is the logger thread, not the caller (log gettid() yourself), and addr2line on optimised binaries misattributes merged inlined frames, so confirm the throw/crash site with a direct probe before acting on it.
- **When diagnosing CI, read the repo at the SHA the runner checked out.** Your working tree is not what CI ran: it can be stale by many commits, and the failing run is often triggered by a commit you have never fetched (a bot's release or merge commit is the common case). Reading a config, manifest, or lockfile at local HEAD then yields a value that contradicts the log and sends you hunting a phantom, or worse, concluding the log is wrong. The checkout step prints the exact SHA it landed on (`git log -1 --format=%H`); fetch that commit and read files with `git show <sha>:<path>`. When a file's contents disagree with what the log implies, suspect you are reading the wrong ref before you suspect the log.
- **An `actions/cache` `!` exclude does nothing if an ancestor directory is also matched.** `resolvePaths` globs the `path:` input with `implicitDescendants: false` and hands the resulting list to `tar --files-from` with no `--no-recursion`, so tar recurses into every directory in that list. The `!` line does drop the file from the glob output, but its parent is still there, and tar puts the file straight back: `target/**` plus `!target/release/bundle/deb/*.deb` caches the .deb regardless. Never express "cache everything except X" this way, since `dir/**` guarantees an ancestor is matched; instead delete X after restore, or cache only the specific subdirectories you want. The failure is silent and can persist for years: verify by resolving the real patterns through `@actions/glob` and taring the result. Suspect this whenever cached build output reappears in artifacts that a clean build could not have produced.
- **Before persisting a build directory across CI runs, check every other caching layer for globs that already cover it.** A build output dir is often declared as an `outputs:` glob by a task runner (turbo's `target/**`, nx, gradle build cache) or listed in an `actions/cache` `path:`, and that layer was harmless only because the dir was empty or small when it ran. Making the dir persistent (sticky disk, rust-cache, a mounted volume) turns that overlap into a multi-GB archive on every run and a stale restore over the live cache, with no error. Grep the task-runner config and workflow cache paths for the directory name first; when there is overlap, relocate the persistent dir outside the tree (`CARGO_TARGET_DIR`, an env override) rather than editing a config the upstream owns. Also check what else hashes that env var: a variable in a task runner's `env` list changes every task hash, so introducing one invalidates the whole remote cache once, including expensive service-backed tasks.
- **A quoted error string in a log is not proof the error fired.** CI runners echo the script before executing it (GitHub Actions prints the whole `##[group]Run` body, `echo "::error ..."` conditionals included, often ANSI-highlighted), so a line containing an error template may just be the source of an un-taken branch. Identify where the annotation was actually emitted (the bare `##[error] ...` line, or the failing command's own stderr) before naming a cause, not where the text merely appears. Mis-reading an echoed conditional as a fired error sends you fixing the wrong thing.
- **Fixing the first failing step of a CI job only unmasks the next one.** A job that has been red at an early step (lint, typecheck) has not executed its later steps for that whole period, so independent failures accumulate there unseen. Before pushing a fix for the first failure, run the job's remaining steps locally in the same order with the same commands, or expect another red run per hidden failure. Observed failure: a rustfmt/prettier fix for a long-red `turbo lint` step went green on lint, then the run died in the next step on a stale `crowdin.yml` entry that the lint failure had been masking. Related signal for prior work: while the shared base branch's CI is red, any sibling PR that recently turned green must be carrying its own copy of the fix, so diff recently-green branches against the base for the files you are about to fix; keyword PR search misses fixes bundled into feature PRs.
- **Before removing, replacing, or reordering a CI setup step, read its log for side effects beyond its stated purpose.** A step that merely "installs tool X" may also be the thing that installs the toolchain on demand, warms a cache, or holds a lock so that later concurrent work never contends. Those effects are invisible in the workflow file and only show in the step's own output (`info: syncing channel updates`, `Cache saved`, `Blocking waiting for file lock`). Grep the step's log in a green run for install, download, cache, and lock lines before touching it, and if it did more than its name says, make that effect explicit in its own step. Observed failure: swapping a `cargo binstall` for a prebuilt download removed the serial, accidental install of the repo's pinned rustup toolchain; the next run's concurrent cargo tasks each tried the install and raced on `~/.rustup/downloads`.
- **A declarative environment entry installs more than the tool it names; read its manifest before adding or removing one.** A devcontainer `features` entry, a plugin/extension pack, or any similar one-line dependency can carry an editor-side payload in its own manifest (`devcontainer-feature.json`'s `customizations.vscode.extensions`), and that payload then indexes, imports, or builds the whole workspace unbidden. There is no way to un-declare what a feature injects, so the only levers are the injected component's own settings or dropping the entry. Before you drop it, judge the injected component by its `activationEvents` and by whether the workspace actually contains the files that trigger it: a language extension for a language the repo does not use never activates, so removing what pulls it in buys nothing and costs whatever else that entry provided. Verify any setting you add to mute it against the extension's own `package.json`, never from memory, since ids and enums do not match intuition (`java.gradle.buildServer.enabled` takes `"on"`/`"off"`, not a boolean). Observed: a monorepo devcontainer's `features/java` silently installed the Java extension pack, which auto-imported ten Gradle projects and sat "Configuring project" downloading toolchains on every codespace open, while `features/go` next to it was inert because the repo had zero `.go` files.
- **A missing CI run is its own failure signature: check workflow state before debugging triggers.** When a workflow that should have fired produces no run at all (as opposed to a failing one), first check whether the workflow itself is disabled (`gh api repos/<owner>/<repo>/actions/workflows` shows `state: disabled_manually`, or `disabled_inactivity` after 60 days without activity) before investigating `paths:` filters, branch filters, or event types; sibling workflows firing on the same paths make a filter explanation implausible anyway. Corollary: a claim that "this PR's own check will verify the fix" is only true once the run actually appears, so confirm the check exists on the PR rather than inferring verification from a merge. Observed failure: a MegaLinter config fix merged with the PR body promising self-verification while the workflow sat manually disabled, so nothing exercised the fix until the state was checked and the workflow re-enabled.
- **When a project's prose and its enforcement disagree, the enforcement wins.** A skill, README, or comment can drift from the CI gate, linter, or schema that actually rejects your change (e.g. a documented file layout that a CI guard now forbids adding). Before following a documented process that touches generated or tool-owned files, confirm it against the mechanism that will gate the PR; if they conflict, satisfy the gate and fix the stale doc in the same effort.
- **A proof of concept must exercise the mechanism the question is about, in the environment it will run in.** When the ask is "can X do Y in Z" (an AI agent converting edits inside CI, a hook firing in the real runner, a tool working on the target OS), a local stand-in that produces the same output by a different route answers a different question and wastes the round-trip. Build the thing where it has to run, with a substitute only for the parts the question is not about. Observed: asked whether AI in CI could turn a human's raw config edits into patch files, a session first shipped a deterministic local extractor and a local boot, which proved the patch primitive but not the CI-agent flow the user wanted, and had to be rebuilt as a real repo, workflow, and PR.
- **When simulating one stage of a pipeline, feed it the inputs the real pipeline delivers before reading its failures.** A stage run in isolation on an empty or synthetic input fails in ways the production path never does, and those failures look like findings. Reconstruct the stage's actual precondition first (the files an earlier stage ships in, the env the wrapper sets, the volume state after install), then run it; only failures that survive that setup are real. Observed: an itzg `PATCH_DEFINITIONS` boot on an empty volume aborted with PathNotFound and skipped a plugin patch, which read as "the patch primitive is broken" until the boot was seeded with the `base/` tree that the pack zip delivers in production, after which every patch applied.
- **Make the failure reproduce without a human before iterating on fixes.** When verification needs a human round-trip (someone wearing a headset, clicking a UI, plugging in hardware), build an autonomous repro first: a self-test that runs the failing path at startup, auto-dismissal of interactive gates, retry loops around known-flaky launches, and a streamed log capture started before launch so rotation can't eat the evidence. Each fix-then-ask-the-human cycle costs minutes and goodwill; the harness pays for itself by the second iteration.
- **A desktop-app frontend can't be verified in a plain browser; pick a runtime-independent surface.** A Tauri or Electron renderer served on its dev port (`localhost:1420` and the like) hard-depends on the native IPC bridge the shell injects (`window.__TAURI__.invoke`, Electron's `ipcRenderer`), so loading that URL in an ordinary browser dies immediately with `Cannot read properties of undefined (reading 'invoke')` and renders nothing. To pixel-verify shared UI components (colours, tokens, layout) without the full native build, render them on a surface that has no runtime dependency: Storybook (check `src/stories/` for existing stories first, most components already have one) or the project's web build. Reach for the native app only when the behaviour under test genuinely needs the shell. When a component lives in a shared package consumed by both a web and a desktop target, the web-renderable surface verifies the exact same code. Corollary for CSS-variable/theme changes: read the computed style off the rendered node (`getComputedStyle(el).borderColor`, plus the resolved `--var` off `:root`) for hue-exact proof instead of eyeballing a screenshot.
- **A desktop app's single-instance guard is keyed on the bundle identifier, not the dev port.** Running a second copy of a Tauri/Electron app (e.g. from a parallel worktree) to test a change will hand off to the already-running instance and exit (`tauri-plugin-single-instance`; SIGTERM / exit 143 right after "Initializing app"), so you end up looking at the *other* checkout's code. Changing the Vite/dev port sidesteps only the port clash, not this one. To run a genuinely independent instance alongside another, also give it a distinct `identifier` in the Tauri/Electron config (a throwaway profile is fine for a visual check), and revert that test-only edit afterwards. Never kill the other session's running app or dev server to reclaim a port/identifier without explicit consent.
- **Capture web-displayed secrets via the OS clipboard, never via the transcript.** When a task needs an API key or token that a web console displays, click the page's own copy button (or select-and-copy) and pipe `pbpaste` straight into the gitignored secrets file, verifying only shape (length, charset, not-equal-to-other-secret), so the value never appears in a screenshot, JS return value, or command output. Two traps: JS-side `navigator.clipboard.writeText` and `document.execCommand("copy")` fail without a real user gesture (a trusted click on the page's copy control works), and pages carry decoy token-shaped fields, notably Laravel's hidden 40-char `_token` CSRF input, so grab by the field's actual id/label and confirm the API accepts the value before declaring it captured.
- **When a bearer-token API hands you a second URL, re-decide auth per host.** APIs like HCP Terraform return follow-up URLs (signed blob downloads, cross-host redirects) whose auth requirements are the opposite of the API's own: the `api/v2` host requires the Authorization header, while the blob/archivist host 401s if you send it (and generic HTTP clients like Python urllib forward headers across redirects, curl strips them cross-host, so the same flow works in one client and fails in another). Follow redirects manually and attach credentials based on the target host, not the original request. Related hygiene: never print raw responses carrying signed URLs or tokens to the transcript; parse them in-script and emit only diagnostics (status, byte counts, names).
- **Stub APIs permissively, capture narrowly.** When a loopback or mock server intercepts an API client to capture requests, return a permissive default (`200 {}` or a minimal valid response object) for unhandled paths, and only persist the body for the specific path you care about. Real clients often probe other endpoints (capability checks, model lookups, version handshakes) before sending the request you want to intercept; a 404 on a pre-flight probe makes them bail before reaching the target path. Reserve 404 for paths that genuinely must not exist.
- **A generator that writes one file per category must own and prune its whole output set.** Codegen that emits `<category>.tf` / `<category>.json` from live data typically writes only the files it has content for, so deleting the last item of a category means nothing rewrites that file and the stale one survives, still declaring things that no longer exist. In an IaC round-trip that silently reverses the deletion: the config still declares the resources while their import blocks are gone, so the next plan recreates exactly what you just deleted. Track the filenames written each run and remove the ones the generator owns but did not emit. Pruning then makes an empty input destructive (zero items of every category reads as every category emptied, so every file gets deleted), so guard the entry point on the input actually being present. Verify by running the generator against a second, unrelated target whose input you did not refresh: if that target's files vanish, the guard is missing.
- **A test suite must survive a fresh clone.** When adding tests that read committed fixtures or goldens, confirm the inputs are actually tracked (`git ls-files <fixture-path>`), then run the suite from a fresh clone or worktree before declaring it done. Broad ignore patterns (`dumps/`, `build/`, `*.json`) silently swallow fixture inputs, leaving a suite that only passes on the authoring machine where the untracked files linger; every other checkout fails with a misleading "input missing" error. If fixture inputs must stay untracked (secrets, size), the test itself must regenerate them, and that regeneration must be code, not a docstring claim.
- **One sample isn't a measurement.** A single run, repro, or test pass doesn't characterise a noisy phenomenon. Before claiming X differs from Y (faster, more reliable, fixed, broken), gather enough samples to see variance, then report it. Applies anywhere outcomes vary: perf benchmarks, flaky tests, network calls, CI on managed infra, A/B comparisons. If you've only got one data point, mark the conclusion provisional, do not open a PR or change production on it.
- **Sanitizing a repo means sweeping derived state with an identifier list, not grepping the obvious keyword.** When stripping org-specific or sensitive content from a repo or vault to make a template, the primary documents are the easy part: tool-generated artifacts echo the deleted content and survive a naive sweep (editor workspace/session state, plugin-generated CSS or config, embedding and search caches, cursor-position and navigation history, metadata exports, AI-agent session logs). Build an explicit identifier list from what you deleted (people, hostnames, project keys, email domains) and grep the entire remaining tree against it until clean, and separately scan every tracked config for credential fields, which live in per-plugin JSON, not in code. Two corollaries: a negated ignore pattern (`!dir/file`) marks a file someone chose to keep, so check for exceptions before bulk-removing the directory it lives in; and scrubbing the working tree does not scrub git history, so a repo whose history carried secrets must be published fresh (orphan branch or new repo) and the exposed credentials rotated regardless.
- **Clone, don't curl.** When reading another repository's source, `git clone` first and read locally. Never `curl` GitHub API endpoints or `curl` raw file URLs to read source, even when docs don't render. (Using `WebFetch` for public documentation pages is fine.) A `WebFetch` summary is a lossy paraphrase: "the documentation does not mention X" is not evidence that X does not happen, so for any behavioural claim you will state as fact (does it delete stale files, does it load this variable) read the implementing source, not the doc summary. Observed: a doc summary said generic packs "don't claim" stale-file removal; the script had done it for years via a manifest file. When a guessed documentation URL 404s, fetch the site's `sitemap.xml` (or its index page) and pick the real path from that, instead of guessing further slugs; each miss is a full round-trip and the sitemap answers in one.
- **All Python through mise.** Never invoke `python`, `pip`, `uv`, or `uvx` directly. Use `mise x -- <command>` for all Python toolchain work. Where no version is pinned, `mise x -- python` fails with `No version is set for shim: python`: pin it inline instead, as `mise x python@<version> -- python ...`. That interpreter carries no third-party libraries (`pyyaml` and friends are absent), so do not assume an import resolves; for a one-off parse, reach for a runtime that already has the parser over installing into it.
- **Never accept a limitation without investigating.** Keep working until the problem is actually solved. Suggesting workarounds as a final answer is not acceptable.
- **Never silence the signal to make CI green.** If a lint rule, security check, or test surfaces real findings during a dep update or refactor, fix the findings, not the alarm. Disabling a linter (e.g. adding to `DISABLE_LINTERS`), broadening an exclude regex, marking a test skipped, or filtering out a real finding in service of an unblocked merge is unacceptable. Genuine false positives can be excluded with a comment naming the specific rule and reason; real findings cannot. If the underlying fix is out of scope for the current PR, leave the PR red with a comment naming the follow-up work, not green with the check muted.
- **Deliver the answer, not instructions to derive it.** When the user asks you to find, fetch, or compute a specific value, produce the value. Do not respond with a snippet for them to run, a formula to apply, or "tell me which one and I'll convert it" when you have the tools to do the lookup yourself. The user delegated the work; punting it back defeats the purpose.
- **A cleanup or migration decision is yours to make; ask only when the answer turns on the user's taste, not on facts you can gather.** Everything in the source existed for a reason, so the default is to carry it across adapted to the new layout, and to delete only what you have shown to be dead, naming the evidence that showed it. Collecting the judgement calls into a question for the user reads as refusing the work, especially when the same investigation that surfaced them would have settled them. Decide, record the reasoning and the evidence where the change is reviewed, and keep each call cheap to reverse. A real preference question is one where two informed people would differ (which product's issue templates a newly shared repo should adopt); a fact question is one the repo answers (whether a config the tool provably never reads should move to where it does), and that one you answer yourself.
- **Act on the operator's diagnosis; don't re-litigate it.** When the person who owns and operates the system gives a clear, actionable instruction or diagnosis, execute it. Do not re-test, re-derive, or "prove" what they have already told you in order to satisfy your own need for certainty, and never reframe a correct instruction as "technically wrong" to score a pedantic point. Verification exists to resolve genuine uncertainty about an unknown, not to second-guess a direct instruction from the system's owner, who usually understands their own setup better than you do. If you genuinely believe the instruction is mistaken, state the specific concern once and let them decide, rather than running experiments to make yourself right. The signal you have crossed this line: the user has to repeat the same instruction more than once, or tells you to just do it. Corollary for automation: when asked to automate a fix the operator already performs manually, replicate their exact mechanism first (same tool, same lever, same order); invent an alternative mechanism only after the direct path is proven closed. Observed failure: hours spent on registry and API EDID writes when the operator's working ritual was an NVCP load plus disconnecting a display, both of which they had already described.
- **Don't say "Docker containers."** Docker is a brand name, not a container type. Write "containers" or "OCI images" in prose. Action references like `docker/login-action` are fine as-is.
- **Never commit secrets.** No API keys, tokens, `.env` files, credentials, or private keys in any repo. If staged accidentally, unstage and remove from history before pushing. If already pushed, rotate the secret immediately; force-push history rewrite only with explicit user confirmation.
- **Never log PII.** No email, phone, name, address, or payment data in logs, traces, or monitoring payloads.
- **No persistent automation without explicit approval.** Never install anything that runs on its own later (scheduled tasks, logon scripts, watchdogs, cron entries, service hooks) unless the user explicitly asked for that specific automation. A monitoring script that "only detects" still counts. Build the on-demand tool; offer the automation; wait for a yes. Observed failure: a logon watchdog deployed unrequested during an HDR fix was revoked by the user with "there will be no watchdog, I never approved that".
- **kustomize discards YAML quoting, so a later-substituted digit string becomes a number.** `FOO: "${appID}"` survives kustomize as bare `FOO: ${appID}`, and envsubst then yields `FOO: 344272`, which the API server rejects for any string-typed field (`Secret.stringData`, container `env[].value`): "got number, want null or string". Block scalars (`|-`) are normalised away too. Fix by keeping the value a real literal in the manifest (kustomize preserves genuine quotes) or by quoting inside the templating layer that runs after kustomize (flux-operator ResourceSets have a `quote` function). Prefer literals for values that are not secret: an app id or installation id is a public identifier, and substituting it buys nothing while adding a failure mode.
- **After variable substitution, check for values that rendered EMPTY, not just for leftover placeholders.** Grepping the output for `${` proves only that nothing was missed syntactically; a variable that was simply not exported substitutes to the empty string and sails through every schema check, then fails at runtime far away (an empty credential surfacing as `Authentication failed`). When you hand-substitute what a controller normally substitutes, diff your variable list against the source of truth, or assert each required key is non-empty in the rendered output.
- **A vendor API returning success is not evidence of effect.** After any state-changing call through a driver or vendor API (NVAPI, IOCTLs, WMI methods), verify by independent readback before building on it; treat "OK" as merely "the call parsed". A tool is not deliverable until its primary mutating path has executed successfully at least once, under a revert guard if the operation is risky; shipping with only the read path tested means the first real user run is the test. Observed failure: NvAPI_GPU_SetEDID returned OK while silently dropping chunked writes (last chunk replaced the whole EDID), and the shipped tool failed on its first real use.
- **Run a retrospective before closing out.** After every non-trivial task, invoke the `retrospective` skill to capture lessons for global memory.

## Memory

| Scope | Deployed path | Edit (source of truth) |
|---|---|---|
| Global cross-tool rules | `~/.agents/AGENTS.md` | `~/.local/share/chezmoi/home/dot_agents/AGENTS.md` |
| Global cross-tool skills | `~/.agents/skills/` | `~/.local/share/chezmoi/home/dot_agents/skills/` |
| Project rules | `./AGENTS.md` (project root or nearest ancestor) | same path |
| Chezmoi repo rules | `~/.local/share/chezmoi/AGENTS.md` | same path |

Always edit the source, not the deployed file. When updating any memory file: review nearby rules for contradictions, duplication, and scope conflicts; reconcile in the same edit. Keep cross-cutting rules in global memory; keep project-specific rules in local memory.

**Before committing a memory (or any dotfiles) update, verify the repo is on its default branch** with `git -C ~/.local/share/chezmoi branch --show-current`. The repo may be parked on an unrelated feature branch; committing there lands the rule off `main` and a `push` creates a stray remote branch. If it is not on the default branch, cherry-pick the change onto `main` (or switch before committing), and leave the feature branch as you found it. **`chezmoi apply` reads the working tree, not git HEAD**, so a repo left parked on a stale/feature branch silently deploys diverged source and can revert a fix that you committed on `main`. After finishing dotfiles work, return the repo to its default branch (or otherwise ensure the working tree carries the fix) so the next apply does not undo it.

## Git and commits

- **Check for prior work before starting a fix.** When the task is to fix a specific CI failure, bug, or pre-described change, scan `gh pr list --state all --search <keywords>` and `git worktree list` before reading code or planning. Previous sessions or parallel agents may already have a branch, open PR, or merged PR matching the scope; duplicating that work wastes effort and risks conflicting changes. Search broadly by feature, version, or symptom, not just your error string: a maintainer's fix is usually titled by the feature it adds ("Fixed X for 26.2"), so a search on the exception message or symbol name misses it. Most important when the fix belongs in a third-party or upstream repo: list that repo's open PRs, especially the maintainer's own, before opening your own, since a redundant competing PR there costs their review time as well as yours.
- **A clean pairwise merge is not proof that two open PRs are compatible.** `git merge-tree --write-tree A B` (exit 0 = no textual conflict) only finds hunks that collide; it says nothing about a PR that adds a gate (validator, lint, schema check, CI step) which the other PR's content violates, or a PR that deletes files another PR's index, manifest, or config still references. When reviewing sibling PRs for overlap, build the merged tree for each pair (`git commit-tree` on the merge-tree output, then a detached worktree) and run every gate any of the PRs introduces against it, the same way CI would. Observed: seven PRs merged pairwise clean, but a validator PR run against the tree merged with a pack-refactor PR reported 17 violations that neither PR's own CI could show.
- Before committing, run `git diff --staged` and confirm the change is atomic and in-scope. Do not commit unrelated modifications.
- **Do not leave completed work uncommitted.** Once a task is implemented and verified, commit the in-scope changes before reporting completion unless the user explicitly asked not to commit or the change is only exploratory. If intent is unclear, ask. Treat pushing separately: ask before pushing unless the user already requested it.
- Commit message format: `type(scope): description`. Types: `feat`, `fix`, `chore`. Check `git log --oneline` to match repo style.
- **A semantic commit footer only counts in the trailing footer block, and its absence is silent.** Tools that read magic footers out of commit messages (release-please's `Release-As: x.y.z`, `BREAKING CHANGE:`) parse with a conventional-commits parser that only treats a token as a footer when it sits in the final block, after the body. Put `Release-As:` in the first body paragraph with prose after it and it parses as body text and is ignored: no error, no release, just "nothing happened" an hour later. Keep semantic footers last, and verify the *actual* commit message (`git log -1 --format=%B`) against the tool's own parser (release-please uses `@conventional-commits/parser`) rather than eyeballing it. When replicating a tool's detection logic to test, confirm the replica first reproduces a known-good example: if every candidate fails, including the documented one, the instrument is wrong, not the input.
- **An empty commit matches no path filter.** `git commit --allow-empty` (the documented way to force a release-please version) touches zero files, so a workflow gated on `paths:` will not fire for it and the release never gets built; trigger the workflow explicitly (`gh workflow run`) afterwards. Related trap: `git commit --amend` on an empty commit refuses with `No changes` unless you pass `--allow-empty`, so an amend you believe rewrote the message can leave the original message in place. Re-read the message after amending.
- **A history-rewriting migration silently de-anchors release automation; re-anchor it before trusting any release PR.** Moving a project into a monorepo (subtree merge, path move) rewrites every commit SHA and usually carries no tags across, which breaks release-please without an error: with no recognizable anchor it walks back to the newest release commit it can still parse and proposes a version *downgrade* whose changelog sweeps in thousands of unrelated upstream commits. Always compare a release PR's proposed version against the version actually shipped before merging. Repair needs both halves: point `last-release-sha` at the rewritten SHA of the last release commit, and create the missing `<component>-v<version>` tag/release, since the config anchor alone leaves release-please logging `looking for tagName: …` / `Expected 1 releases, only found 0`. Two follow-on traps in the same setup: a package that is not at the repository root namespaces the action's outputs per path (`launcher--version`, not `version`), so downstream publish jobs reading `.version` receive an empty string and fail their guard only after the expensive build jobs have already succeeded; and re-running a release after deleting a bad tag also requires flipping the merged release PR's label from `autorelease: tagged` back to `autorelease: pending`, or release-please considers it released and skips.
- **A green release workflow is not a shipped release; verify at the surface consumers actually read.** Job conclusions describe steps, not outcomes, and release pipelines routinely fan out so that artifact builds pass while the publish job that uploads them fails. Confirm a release by fetching what users will fetch: the update manifest (check the version field and that per-platform signatures are non-empty) and a `HEAD` of every artifact URL it advertises, asserting a plausible `content-length` rather than just a 200. Note where the artifacts are expected to live before concluding anything: a GitHub release carrying zero assets is a red flag when the workflow attaches binaries to it and completely normal when the workflow uploads them to a CDN or bucket instead, so check a known-good previous release to establish the baseline.
- After any branch switch (including `gh pr checkout`), verify with `git branch --show-current`. If `gh pr checkout` fails or lands on the wrong branch, use `git checkout <branch>` directly.
- A stale `.git/index.lock` blocks all git operations. Remove it with `rm -f .git/index.lock` before retrying the blocked command.
- **Worktree context.**
    - When the cwd is inside a Claude Code worktree (e.g. `.claude/worktrees/<id>`), git and gh commands act on the worktree branch. The main repo's working tree may be locked by another agent; do not `git checkout` or `gh pr checkout` against it.
    - To pull a PR branch, materialize it into a new worktree: `git -C /path/to/main-repo fetch origin <branch> && git -C /path/to/main-repo worktree add <path> origin/<branch>`.
    - Use `git -C <path>` for all subsequent commands. Confirm the active branch with `git -C <path> branch --show-current` before reading or editing files.
    - **Anchor subagent commands to the worktree explicitly.** When dispatching subagents from inside a worktree, include `cd <absolute-worktree-path> && <command>` (or pass absolute paths) in every Bash invocation in the subagent's prompt. Subagents may run from a different effective cwd than the controller, and from a sibling main repo at a parent path you get superficially plausible but wrong git/file answers (e.g. a staged file reported as unstaged, a CRLF-free file reported as CRLF, HEAD reported as a different commit). The signal that you've hit this: the subagent reports a state that contradicts what you can directly verify yourself, and re-dispatching with explicit anchoring makes the contradiction disappear.
    - **`gh pr close --delete-branch` and `gh pr merge --delete-branch` check out the default branch locally first.** Inside a worktree that fails with `'main' is already used by worktree at ...`, aborts the rest of a `&&` chain, and leaves the remote branch in place. From a worktree, close or merge without the flag and delete the branch with `git push origin --delete <branch>` plus `git branch -D <branch>`.
- **After a PR merges, proactively offer to clean up its worktree and branches.** When the user confirms a PR has been merged (or you observe the merge while working), surface a cleanup offer via `AskUserQuestion` before doing anything destructive. The cleanup is: `git worktree remove <path>`, `git branch -D <name>` locally, and `git push origin --delete <name>` (often a no-op because GitHub auto-deletes the head branch on merge). Refuse to delete dirty worktrees without explicit per-tree consent. If the current shell's CWD is inside the worktree being removed, expect a "Permission denied" on the directory itself: the git entry, contents, and branches still get cleaned, leaving only an empty husk that vanishes once the shell exits.
- **No AI attribution in `headlesshq` repositories.** The `headlesshq` org maintainer (okafke) has explicitly asked that Claude not appear as a contributor in their repos (mc-runtime-test, headlessmc, etc.), citing community animosity toward AI. In any `headlesshq` repo this overrides the default co-author trailer: omit the `Co-Authored-By: Claude` line from commits and drop the `🤖 Generated with Claude Code` / `🤖 Addressed by Claude Code` lines from PR bodies and review replies. If such a trailer already reached a branch, removing it via history rewrite plus force-push is warranted there even on an open PR (the maintainer requested it).
- **Committed entrypoint scripts must keep their executable bit.** When adding, moving, or renaming a script that CI or a hook invokes as `./script` (`gradlew`, `mvnw`, `*.sh` entrypoints), confirm the tracked mode is `100755`, not `100644`, with `git ls-files -s <path>`. A non-executable `gradlew` fails CI with `./gradlew: Permission denied` (exit 126). `git mv` preserves whatever mode the source already had, so renaming a directory does not fix a pre-existing bad mode, and a sibling version that works is the reference to compare against; set it with `git update-index --chmod=+x <path>`.
- **Cloning for tag comparison.** `--depth=1 --no-single-branch` does not fetch tags. When you need to compare specific tags, either clone without `--depth`, or run `git fetch --tags` after the shallow clone.
- **Never `--depth` a fetch into a repo you will keep working in.** `git fetch origin <sha> --depth=1` inside an existing full clone silently marks the *whole* repository shallow (creating `.git/shallow`), severing history: `git merge-base` then returns nothing and `git merge --ff-only origin/main` fails with `refusing to merge unrelated histories`. The damage surfaces a step later and reads as a branch or upstream problem, not as fallout from your own fetch. When you only need one commit's contents from a repo you also intend to branch, merge, or diff in, fetch without `--depth`. If a repo is already shallow, repair it with `git fetch origin --unshallow` before trusting any history operation.
- **A missing PR base branch is not yours to manufacture.** When a task names a base branch that `git ls-remote --heads origin <name>` does not show, do not push someone else's local branch to create it: a branch checked out in another worktree (`git worktree list`, `+` in `git branch`) is a human's live work, and they may be rebasing or squashing it right then, so what you push is a stale WIP tip that races their push and forces a rebase of your own work. Branch from the local tip, and re-run `git ls-remote` immediately before opening the PR: if the base has appeared, rebase onto it (`git rebase --onto origin/<base> <old-local-tip>`); if it is still missing, target the default branch and say so in the PR body. Observed failure: pushed a local `feat/preview-mvp` WIP tip as the PR base while the owner was pushing its cleaned-up replacement; the PR branch then had to be rebased across a conflicting README.
- **Inspecting a PR's diff.** Always diff the remote PR branch against `origin/main` (e.g. `git diff origin/main...origin/<pr-branch>`), not local HEAD. Local HEAD may be on an unrelated branch, so a diff against it is meaningless and returns empty output without any error. Use three dots (`...`), not two: even against `origin/main`, a two-dot `origin/main..branch` conflates the branch's stale merge-base with its own changes, so a branch cut from an older main shows edits to whole subtrees the PR never touched and will mislead any per-area or path-filter reasoning; three-dot shows only the PR's own changes, which is also what GitHub uses for path-filtered CI and for review.
- **A lockfile's git diff overstates version churn; compare resolution-key sets instead.** Removing a workspace importer or a dependency rehashes pnpm/yarn peer-dependency suffixes, so unchanged entries move position and appear as paired `+`/`-` lines (and repositioned blocks read as "hundreds of new packages") even though nothing was bumped. To judge whether an install actually changed versions, extract the full set of `package@version` keys from the old lockfile (`git show HEAD:<lock>`) and the new one and diff those sets, not the git diff. A naive diff read makes a pure prune look like churn and can send you reverting a correct regeneration.
- **A `pull_request_target` (or other base-ref) workflow fix cannot go green on its own PR.** Workflows triggered by `pull_request_target` execute the definition, and use the secrets, from the *base* branch, not the PR head. A change to such a workflow (or a fix depending on a newly-added secret) therefore has zero effect on its own PR's check, which stays red until merged. Do not chase that green check or assume the fix is broken: confirm the failure is the unchanged base-branch error, land the PR, then validate on the base via `workflow_dispatch` or the next PR. Note this in the PR body so reviewers do not read the red check as a real failure.
- **A workflow that should have triggered but produced no run at all may be disabled, not mis-filtered.** Before debugging a workflow's `on:`/`paths:` because its check never appears on a PR, check its state: `gh api repos/<owner>/<repo>/actions/workflows/<id> --jq .state` returns `disabled_manually` for one that was turned off, and a disabled workflow silently never runs regardless of triggers or path matches (no skipped check, no run, nothing). The trap compounds when several workflow files share a `name:` (e.g. three files all named `CI`): `gh workflow list` shows indistinguishable rows, and `gh workflow enable/disable <NAME>` (or identifying a run by name) acts on an arbitrary one, so a cleanup meant to disable a stale duplicate can silently disable the live workflow instead. Operate on workflows by numeric id or file path, never the display name, and re-read `.state` afterwards. Corroborating signal: the commit's `github-actions` check-suite shows `completed/success` with only unrelated checks present.
- **Before opening a PR: clean up history.** Squash messy work-in-progress or AI-attributed commits into a clean, atomic commit sequence on the branch. The branch is yours until `gh pr create` succeeds.
- **Squash onto the base you branched from, not onto a freshly fetched tip.** `git fetch` then `git reset --soft origin/main` followed by `git add -A` folds the reverse of everything merged to main since you branched into your commit, so the PR silently reverts other people's work (observed: 90 files, launcher and workflow changes deleted). Squash with `git merge-base origin/main HEAD` as the base, or rebase the branch onto the new tip first and only then squash; before pushing, confirm `git diff --name-only origin/main` lists only files you meant to touch.
- **`git push origin <branch>` during an unfinished rebase pushes the old ref.** While a rebase is stopped (conflict, `--skip` that did not complete), the branch ref still points at the pre-rebase commit and HEAD is detached on the partial result, so a `--force` push of the branch name publishes the old history while your terminal shows the new one. Check `git status` says no rebase is in progress (and `git rev-parse HEAD` equals `git rev-parse <branch>`) before any push after a rebase.
- **Once a PR is open: never amend or force-push.** Use follow-up commits so reviewers see exactly what changed between their review and your response. The branch now belongs to the reviewer; rewriting it erases the diff they expect to see. Preserve every change as a separate commit.
- **Renovate auto-merge needs platform prerequisites, not just `automerge: true`.** With a restrictive top-level `schedule`, Renovate's own merge step only runs inside that window, so green PRs can sit unmerged for days. To merge whenever checks pass, rely on GitHub-native auto-merge (`platformAutomerge`, default true): it requires the repo's "Allow auto-merge" setting enabled AND branch protection on the target branch with the CI checks marked required. Set those required checks non-strict (do not require the branch be up to date) so a rebase schedule cannot deadlock merges, and leave admins exempt so the owner's direct pushes still work. Diagnose "automerge configured but PRs piling up" by correlating the last successful auto-merge against recent `schedule`/config commits, then verify the fix non-destructively by enabling auto-merge on a failing PR: GitHub should accept it but hold it (BLOCKED), not merge.
- **A file committed as raw bytes but tracked by LFS blocks pull/rebase and shows perpetually modified.** When `.gitattributes` marks a path `filter=lfs` yet the committed blob is the real content rather than a pointer, git's clean filter re-derives a pointer on every comparison and never matches the committed blob, so the file reads as "modified" even right after `checkout`, and `git pull` / `rebase` / autostash abort with `Encountered N file(s) that should have been pointer(s), but weren't`. Do not fight it with repeated `checkout`/`stash`/move-aside attempts. Run the blocked operation once with the LFS filters neutralised: `git -c filter.lfs.clean=cat -c filter.lfs.smudge=cat -c filter.lfs.process= -c filter.lfs.required=false <pull|rebase|checkout>`. That bypass also leaves any newly-fetched LFS paths as pointer stubs, so finish with `git lfs pull` (or `git lfs checkout <paths>`) to re-materialise real content, and confirm none remain with `git lfs ls-files | grep -c ' - '` (expect `0`). The repo-level fix, when you own the file, is to re-commit it as a proper pointer (`git add --renormalize <path>`) so the mismatch stops recurring.
- **A "diverged" local branch may just be stale from squash-merges.** When a local branch (often `main`) reports N ahead / M behind and a rebase conflicts, do not assume the local commits are valuable unpushed work. Squash-merged commits keep their original SHAs locally but get a different patch-id upstream, so `git cherry` / patch-id matching reports them as "not upstream" even when their content is already merged (the rebase itself may still auto-drop a few as "already upstream"). Verify by content against the upstream tip (`git diff origin/main HEAD -- <file>`, or grep the upstream blob for the feature), not by patch-id. If the work is already upstream, back up the branch then reset it to the upstream tip and cherry-pick only the genuinely-new commits, rather than rebasing: replaying superseded commits conflicts needlessly and can regress later upstream fixes (for example a CI repair that touched the same files).

## Shell discipline

- Prefer the smallest atomic command that completes the immediate next step. Do not chain concerns across policy boundaries.
- **Kill by listener, never by port.** `lsof -ti tcp:<port>` lists every process with a socket on that port, including your own services holding a keep-alive *client* connection to it, so `lsof -ti tcp:<port> | xargs kill` to restart a backend also kills the proxy or console you were testing through, which then reads as a mysterious clean exit of the wrong process. Use `lsof -ti tcp:<port> -sTCP:LISTEN` (or the pid you recorded at launch) when stopping a local server.
- Destructive or policy-sensitive actions should be isolated so intent is easy to inspect.
- **Never truncate the output of a mutating command.** Piping `git push`, `gh`, `kubectl apply`, or any other state-changing call through `| tail -1` or `2>/dev/null` hides the one line that says why it was rejected, so a failure costs a blind retry instead of a diagnosis. Keep the full stderr for anything that changes state, and reserve `head`/`tail` trimming for read-only listings. Observed failure: three `git push --force-with-lease` calls inside a loop were reported only as `failed to push some refs`, and the cause was never seen because the rejection line had been trimmed away; the retry outside the loop succeeded with no explanation.
- Do not check whether a directory exists before using it. Attempt the operation; create the directory if it fails.
- **Never bare `cd` in an agent shell call.** The working directory persists across calls, so `cd sub && test.sh` silently moves every later command, and a batch of relative-path validations then fails with `No such file` or, worse, inspects the wrong tree. Use `(cd sub && …)` or absolute paths; if a call must change directory, restore it in the same call.
- **Test a command in the shell that will actually run it.** The Bash tool here is zsh, while CI `run:` steps are typically `bash -e`, and the two disagree in ways that fake a failure. zsh aborts on an unexpanded glob (`no matches found`, nonzero exit) where bash passes the pattern through literally, so a perfectly safe `rm -rf foo/*/bar` reports a false failure locally and tempts you to "fix" a command that was never broken. Run the real thing (`bash -c '...'` or `bash script.sh`) before concluding anything about a snippet destined for bash. zsh also performs `=word` expansion on unquoted words beginning with `=` (a `=cmd` PATH lookup), so a bare separator like `echo ===` fails with `== not found`: quote such literals. Generally: when validating a snippet for another runtime, reproduce that runtime's semantics rather than trusting your interactive shell's. zsh also does not word-split an unquoted `$VAR`, so a command stored in a variable (`K="mise x -- kubectl"; $K get pods`) fails with `command not found: mise x -- kubectl`; define a shell function instead, or run the snippet under `bash`. The glob abort also bites read-only investigation: an unquoted glob-shaped option value (`grep --include=*.md`) aborts that whole command line in zsh, so empty output means "the search never ran", not "nothing matched". Quote such values (`--include='*.md'`), and when a `no matches found` line appears anywhere in a compound command, treat every conclusion drawn from its output as unverified and re-run.
- **Never edit a file with `perl -pi -e 's|...|...|'` when the text contains `|`.** With `|` as the delimiter, a literal pipe in the pattern or replacement (jq programs, template filters like `<< x | quote >>`, `||` in shell) silently truncates the match and splices the replacement at the wrong spot, leaving the old block behind and the file syntactically broken, sometimes with the fragment inserted at line 1. The edit reports success. Use a delimiter that cannot occur in the text (`s{...}{...}`), a line-addressed tool (`sed -i 'N,Md'`, awk by line number or by exact anchor line), or rewrite the whole file from a heredoc; then run a syntax check (`bash -n`, `yq`, `kubeconform`) before committing. Observed: three separate corruptions of one script and one manifest in a single session from this pattern.
- **A validation gate inside a pipeline needs `set -o pipefail`.** `set -e` only sees the last command of a pipeline, so `render | tool > out` failing in `render` leaves a stale or empty `out`, the following checks validate the wrong artifact, and the commit and push proceed. Use `set -eo pipefail` for any chain that gates a commit, and check the produced artifact has the content you expect (`grep -q kind: Deployment out`) rather than only that a tool exited 0. The same masking hits ad-hoc verification in the agent shell: `validator … | tail -15` reports `tail`'s exit 0 even when the validator never ran (observed: `timeout` does not exist on macOS, so `timeout 540 npx … | tail` printed `command not found` and exit 0, and the config was reported validated). For any run whose exit code you will cite, write output to a file and read it, or prefix `set -o pipefail`, and read the captured output rather than the status alone.
- **A `&&` chain ending in `|| true` reports success for steps that never ran.** In `a && b && c || true`, a failure in `a` skips `b` and `c` entirely and the trailing `|| true` then reports the whole thing green, so the tail silently no-ops forever with no error anywhere. This is the standard shape of devcontainer lifecycle hooks, Dockerfile `RUN` lines, and CI `run:` steps, where the skipped tail is usually the step that actually mattered (writing secrets, seeding config). Give each concern its own named step rather than chaining unrelated ones (devcontainer lifecycle hooks take an object form whose entries run in parallel and are reported individually), and reserve `|| true` for the single command whose failure is genuinely tolerable. Where a step can legitimately do nothing, make it say so loudly: a script that prints `Skipping X` and exits 0 is indistinguishable from one that never ran, so print a summary block naming what was missing and how to supply it.
- **On Windows, do not author scripts through Bash heredocs; use the file-write tool.** The Git Bash tool there collapses doubled backslashes inside quoted heredocs, so PowerShell or C# written via `cat <<'EOF'` arrives with `\\` turned into `\`, breaking regex escapes and path literals with confusing parse errors several steps later. The corruption survives the quoted-heredoc form that normally guarantees verbatim text. Write script files with the dedicated file-write tool (or avoid backslash escapes entirely, for example `[char]92` in PowerShell); reserve heredocs for content with no backslashes. The signal: a script fails with "Illegal \ at end of pattern" or similar escape errors that do not match the source you wrote.
- On Windows, when admin rights are required, launch elevated commands with `Start-Process -Verb RunAs` instead of failing back to manual instructions.
- On Windows, use the Bash tool (not PowerShell) for POSIX-style commands like `grep`, `find`, `head`, `tail`, and path operations that use forward slashes. Use PowerShell only when you need Windows-native cmdlets, `$env:` variables, or paths with backslashes that POSIX tools cannot handle.
- On Windows, POSIX-style paths like `/tmp/...` resolve only inside the Bash tool. Native filesystem tools (read/edit/write/grep/glob in any agent harness) use Windows file APIs and need Windows-style paths (`C:\...` or `C:/...`). When a Bash command reports a canonical path (e.g. `Cloning into 'C:/Users/.../Temp/repo'`), use that path for subsequent tool calls; do not reuse the `/tmp/` shortcut.

## Toolchain

- When a CLI can be managed by `mise`, run it through `mise x -- <command>`. Do not invoke managed tools directly.
- When entering a new worktree that has a `mise.toml` or `.mise.toml`, run `mise trust <worktree-path>/{mise,.mise}.toml` (or the specific file present) before any `mise x --` call. Otherwise every mise invocation fails with `Config files in <path> are not trusted`.
- **mise `[env]` is directory-scoped and beats your exported variables.** `mise x` re-applies the `[env]` block of the nearest config (for example `KUBECONFIG = "{{config_root}}/kubeconfig"`) on top of the shell environment, so an `export KUBECONFIG=...` you set is silently replaced, and the same command run from a different cwd (repo root instead of the subtree) gets no env at all and fails a step later with an unrelated-looking error (`current-context is not set`, `the server could not find the requested resource`). Put the file where the config expects it and run from that directory. A fresh worktree does not carry gitignored local files (`kubeconfig`, `age.key`, `.env`): copy them from the main checkout or a sibling worktree before the first `mise x` call.
- **`mise x -- go install` puts binaries in mise's GOBIN, not `$HOME/go/bin/`.** mise's Go install has its own GOBIN (typically `<mise root>/installs/go/<ver>/bin/`), so binaries installed through `mise x -- go install ...` do not appear under `$HOME/go/bin/`. Scripts that fall back to `$HOME/go/bin/<tool>` will not find them. Either set `GOBIN=$HOME/go/bin mise x -- go install <pkg>` to land it there, or copy the resulting `<mise root>/installs/go/<ver>/bin/<tool>` into `$HOME/go/bin/` after install.
- **Git hooks inherit the invoker's PATH, so mise-managed hook tools need mise activation.** When `pre-commit`, `bats`, or any other mise-managed binary is wired into `.git/hooks/*`, running `git commit` from a shell without mise on PATH fails with `<tool> not found.  Did you forget to activate your virtualenv?` (or similar). Wrap the commit in `mise x -- bash -c 'git commit ...'` so the hook subprocess inherits the shim path; this is the default workaround whenever the Bash tool's plain PATH is missing mise's tools.
- **Gradle Kotlin DSL task actions must not touch script-level `val`s.** With the configuration cache on, a `doLast {}`/`doFirst {}` lambda that reads a top-level script property (a URL string, a `layout.buildDirectory` provider) captures the script object itself, and the build fails with `cannot serialize Gradle script object references`; the same applies to unqualified `uri()`, `file()` and other `Project` helpers inside the action. Copy what the action needs into locals inside the `tasks.registering {}` block before the `doLast`, and use plain JDK calls (`java.net.URI.create`, with an explicit `import` since bare `java.` resolves to the `java {}` extension in a `.kts` script). Verify with a clean build, not a re-run: an up-to-date task never re-executes the offending action, so the failure only shows once the cache entry is stored.
